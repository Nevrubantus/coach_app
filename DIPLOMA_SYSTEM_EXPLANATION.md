# Объяснение информационной системы для предзащиты и защиты

Этот документ написан обычным языком, чтобы можно было не просто прочитать код, а объяснить, как устроена система учета, анализа и контроля спортивных тренировок.

## 1. Что делает система в целом

Проект представляет собой информационную систему для ведения спортивных тренировок. В системе есть две роли:

- спортсмен;
- тренер.

Спортсмен может:

- зарегистрироваться, подтвердив согласие на обработку персональных данных, и войти в аккаунт;
- вести свой профиль: имя, телефон или почта, рост, вес, возраст, фото;
- создавать тренировки на нужную дату и время;
- добавлять в тренировку упражнения;
- добавлять подходы: рабочий вес, количество повторений, заметки;
- прикреплять видео к каждому подходу;
- видеть на главной странице своего закрепленного тренера с фото, именем и контактом;
- читать комментарии тренера к видео в удобном виде: слева фото и имя тренера, справа текст рекомендации;
- смотреть свои прошлые и предстоящие тренировки;
- смотреть график прогресса рабочего веса по упражнениям;
- смотреть график изменения собственного веса;
- пользоваться библиотекой упражнений с изображениями и подробным описанием техники.

Тренер может:

- зарегистрироваться и войти как тренер;
- редактировать свой профиль и фото;
- закреплять спортсменов за собой по телефону или почте;
- видеть список закрепленных спортсменов с их фотографиями;
- открыть спортсмена и посмотреть его тренировки и данные профиля;
- назначить спортсмену новую тренировку;
- редактировать предстоящие тренировки спортсмена;
- смотреть прошедшие тренировки спортсмена;
- открывать видео подходов, которые загрузил спортсмен;
- оставлять комментарии к видео;
- смотреть динамику рабочих весов спортсмена.
- вести собственный спортивный профиль: рост, вес, возраст;
- создавать и заполнять свои личные тренировки, упражнения, подходы и повторения;
- смотреть свой график прогресса и веса тела.

Если объяснять совсем просто: спортсмен заполняет, что он сделал в зале, а тренер видит эти данные, проверяет видео и дает обратную связь. При этом тренер тоже может тренироваться как обычный пользователь системы: его тренировки сохраняются за его же аккаунтом тренера и не превращают спортсменов в тренеров.

## 2. Общая архитектура

Система разделена на три основные части:

1. Мобильное/веб-приложение Flutter.
2. Сервер Serverpod.
3. База данных PostgreSQL.

Дополнительно есть автогенерируемый клиент `coach_app_client`, который связывает Flutter-приложение с сервером.

Схема работы такая:

```text
Пользователь
   |
   v
Flutter-приложение
   |
   | вызывает методы client.user / client.training / client.coach
   v
Serverpod-сервер
   |
   | читает и записывает данные
   v
PostgreSQL база данных
```

Отдельно видео и фотографии профиля хранятся не прямо в базе, а как файлы на сервере:

```text
Видео подхода
   -> сохраняется в папку web/static/uploads/videos
   -> в базе хранится путь к файлу, название, дата загрузки и связь с подходом

Фото профиля
   -> сохраняется в папку web/static/uploads/avatars
   -> в таблице app_user хранится путь к файлу в поле imagePath

Фото упражнений, добавленных администратором
   -> сохраняются в папку web/static/uploads/exercises
   -> в таблице exercise хранится путь к файлу в поле mediaUrl
```

Так сделано потому, что большие видеофайлы и изображения неудобно хранить прямо в таблицах базы данных. В базе лучше хранить только информацию о файле и путь к нему.

## 3. Почему выбран Serverpod

Serverpod удобен для такого проекта, потому что он сразу дает:

- сервер на Dart;
- генерацию клиентского кода для Flutter;
- работу с PostgreSQL;
- миграции базы данных;
- модели данных через `.spy.yaml`;
- endpoints, то есть серверные методы, которые клиент вызывает почти как обычные Dart-функции.

Например, во Flutter можно вызвать:

```dart
client.training.listWorkouts(userId)
```

А на сервере этому соответствует метод:

```dart
Future<List<Workout>> listWorkouts(Session session, int userId)
```

То есть Flutter не пишет SQL-запросы напрямую. Он обращается к серверу, а сервер уже безопасно работает с базой.

## 4. Роли пользователей

Роль хранится в таблице `app_user` в поле `isAthlete`.

- `isAthlete = true` - это спортсмен.
- `isAthlete = false` - это тренер.

После входа приложение смотрит роль пользователя и открывает нужный интерфейс:

- спортсмен попадает в обычную навигацию с главной, тренировками, графиком и профилем;
- тренер попадает в панель тренера.

За это отвечает файл `coach_app_flutter/lib/main.dart`, особенно класс `RoleGate`.

### Администратор без отдельного интерфейса

Отдельный экран администратора в мобильном приложении не нужен. В демонстрационной версии администратор - это человек, у которого есть доступ к серверной папке и Docker. Он управляет ролями и привязками через серверную консоль:

```bash
cd coach_app_server
dart bin/admin.dart users
dart bin/admin.dart links
dart bin/admin.dart exercises
dart bin/admin.dart set-role <contact> <trainer|athlete>
dart bin/admin.dart attach <coach_contact> <athlete_contact>
dart bin/admin.dart detach <coach_contact> <athlete_contact>
dart bin/admin.dart add-exercise --name "Гиперэкстензия" --description "Описание техники" --photo "C:\path\photo.jpg"
dart bin/admin.dart update-exercise <id> --description "Новое описание" --photo "C:\path\photo.jpg"
dart bin/admin.dart delete-exercise <id>
```

Так администратор может посмотреть всех пользователей, назначить пользователю роль тренера или атлета, увидеть текущие связки, вручную привязать или отвязать атлета от тренера, а также управлять справочником упражнений. Он может добавить новое упражнение, изменить описание техники, прикрепить фотографию или удалить упражнение из библиотеки. Это не пользовательская функция приложения, а служебный инструмент сопровождения системы. Обычный спортсмен и обычный тренер из мобильного приложения не получают такие права.

## 5. База данных простыми словами

База хранит основные сущности системы: пользователей, тренировки, упражнения, подходы, видео и комментарии.

### Таблица `app_user`

Модель: `User`.

Хранит аккаунт пользователя.

Поля:

- `name` - имя пользователя;
- `contact` - телефон или email, используется как логин;
- `password` - не сам пароль, а его хэш в формате `sha256:v1:...`;
- `isAthlete` - роль пользователя;
- `height` - рост спортсмена;
- `weight` - текущий вес спортсмена;
- `age` - возраст;
- `imagePath` - путь к фото профиля на сервере, например `uploads/avatars/avatar_1_...jpg`;
- `imageScale` - масштаб фото внутри круглого аватара;
- `imageOffsetX` - сдвиг фото по горизонтали внутри аватара;
- `imageOffsetY` - сдвиг фото по вертикали внутри аватара.

Важно: `contact` уникален. Два пользователя не могут зарегистрироваться с одним и тем же логином.

### Таблица `coach_athlete`

Модель: `CoachAthlete`.

Это связующая таблица между тренером и спортсменом.

Поля:

- `coachId` - id тренера;
- `athleteId` - id спортсмена;
- `createdAt` - дата закрепления.

Зачем нужна отдельная таблица: один тренер может вести нескольких спортсменов. В будущем один спортсмен тоже может быть связан с разными тренерами, если это потребуется.

### Таблица `exercise`

Модель: `Exercise`.

Хранит библиотеку упражнений.

Поля:

- `name` - название упражнения;
- `description` - описание техники;
- `mediaUrl` - путь к картинке упражнения;
- `mediaType` - тип медиа, сейчас это `image`.

Базовые упражнения создаются сервером автоматически, если их еще нет в базе. При этом библиотека больше не ограничена только этими базовыми упражнениями: администратор может добавлять новые записи через `dart bin/admin.dart add-exercise`. После этого спортсмены и тренеры увидят новое упражнение в общей библиотеке, потому что экран библиотеки вызывает `client.training.listExercises()` и получает актуальные данные из таблицы `exercise`.

Примеры упражнений:

- жим штанги лежа;
- отжимания на брусьях;
- подъем штанги на бицепс;
- жим гантелей сидя;
- тяга верхнего блока к груди;
- скручивания на скамье;
- приседания со штангой;
- жим ногами в тренажере.

### Таблица `workout`

Модель: `Workout`.

Это сама тренировка.

Поля:

- `userId` - чей это план, то есть id спортсмена;
- `title` - название тренировки;
- `scheduledAt` - дата и время тренировки;
- `durationMinutes` - длительность;
- `notes` - заметки;
- `isCompleted` - завершена тренировка или нет.

Одна тренировка принадлежит одному спортсмену.

### Таблица `workout_exercise`

Модель: `WorkoutExercise`.

Это упражнение, добавленное в конкретную тренировку.

Поля:

- `workoutId` - id тренировки;
- `exerciseId` - id упражнения из библиотеки;
- `exerciseName` - название упражнения на момент добавления;
- `orderIndex` - порядок упражнения в тренировке;
- `notes` - заметки.

Зачем хранить `exerciseName` отдельно: если название упражнения в библиотеке когда-нибудь изменится, в старой тренировке все равно останется понятная запись.

### Таблица `workout_set`

Модель: `WorkoutSet`.

Это подход внутри упражнения.

Поля:

- `workoutExerciseId` - к какому упражнению тренировки относится подход;
- `setIndex` - номер подхода;
- `weight` - рабочий вес;
- `reps` - количество повторений;
- `notes` - заметка спортсмена;
- `createdAt` - когда подход записан.

Именно из этих данных строится график прогресса рабочего веса.

### Таблица `workout_video`

Модель: `WorkoutVideo`.

Хранит информацию о видео, прикрепленном к подходу.

Поля:

- `workoutId` - тренировка;
- `workoutExerciseId` - упражнение в тренировке;
- `workoutSetId` - конкретный подход;
- `athleteId` - спортсмен, который загрузил видео;
- `fileName` - исходное имя файла;
- `filePath` - путь к файлу на сервере;
- `uploadedAt` - дата загрузки.

Сам файл лежит в `coach_app_server/web/static/uploads/videos`.

### Таблица `video_comment`

Модель: `VideoComment`.

Хранит комментарии тренера к видео.

Поля:

- `videoId` - к какому видео относится комментарий;
- `coachId` - какой тренер оставил комментарий;
- `coachName` - имя тренера;
- `text` - текст комментария;
- `createdAt` - дата комментария.

Спортсмен открывает видео и видит комментарии тренера.

Важно: в самой таблице комментария не дублируется фотография тренера. Комментарий хранит `coachId`, а приложение по этому id берет пользователя из `app_user` и показывает его актуальное фото из `imagePath`. Поэтому если тренер поменяет фото профиля, старые комментарии тоже будут отображаться уже с новым фото.

### Таблица `body_weight_entry`

Модель: `BodyWeightEntry`.

Хранит историю собственного веса спортсмена.

Поля:

- `userId` - спортсмен;
- `weight` - вес;
- `measuredAt` - дата измерения.

Когда спортсмен меняет вес в профиле, сервер добавляет запись в историю веса. Потом из этих записей строится график веса тела.

### Модель `ProgressPoint`

Это не таблица базы данных, а расчетная модель.

Она нужна, чтобы передать во Flutter готовую точку графика:

- дата;
- название упражнения;
- рабочий вес.

Сервер берет подходы из тренировок, выбирает максимальный рабочий вес по упражнению и возвращает список таких точек.

## 6. Как работает спортсменский сценарий

1. Спортсмен регистрируется.
2. Данные уходят на сервер в `UserEndpoint.register`.
3. Сервер проверяет, свободен ли логин.
4. Если логин свободен, пользователь сохраняется в базе.
5. Flutter сохраняет данные сессии локально через `SharedPreferences`.
6. После входа `RoleGate` открывает спортсменскую часть приложения.
7. На главной спортсмен видит:
   - приветствие;
   - мотивационный блок;
   - карточку закрепленного тренера с фото, именем и контактом;
   - ближайшую тренировку;
   - статистику за месяц;
   - текущий рабочий вес;
   - антропометрию;
   - блоки с графиками.
8. В календаре спортсмен создает тренировку.
9. Внутри тренировки добавляет упражнения из библиотеки.
10. В упражнение добавляет подходы.
11. К подходу может прикрепить видео.
12. Если тренер оставил комментарий к видео, спортсмен видит его в блоке видео: слева небольшая фотография и имя тренера, справа текст комментария.
13. После внесения веса сервер может использовать эти данные для графика прогресса.

## 7. Как работает тренерский сценарий

1. Тренер входит в аккаунт с ролью тренера.
2. `RoleGate` открывает `CoachDashboardScreen`.
3. На главном экране тренер видит список закрепленных спортсменов. В карточке каждого спортсмена показывается его фото профиля, если оно загружено.
4. Чтобы закрепить спортсмена, тренер вводит телефон или email спортсмена.
5. Серверный метод `attachAthleteByContact` проверяет:
   - существует ли тренер;
   - действительно ли это тренер;
   - существует ли спортсмен с таким контактом;
   - действительно ли это спортсмен;
   - нет ли уже такой связи.
6. После закрепления создается запись в `coach_athlete`.
7. Тренер нажимает на спортсмена и видит:
   - шапку спортсмена с его фото, именем и контактом;
   - предстоящие тренировки;
   - прошедшие тренировки;
   - график прогресса.
8. Тренер может назначить тренировку спортсмену.
9. Если тренировка прошедшая, тренер открывает ее, смотрит видео подходов и оставляет комментарии.
10. Комментарий сохраняется с id тренера, поэтому спортсмен потом видит не просто текст, а автора комментария: фото тренера, имя тренера и саму рекомендацию.

## 8. Как работает видео

Видео прикрепляется к конкретному подходу.

Порядок такой:

1. Спортсмен открывает тренировку.
2. У упражнения добавляет подход.
3. Нажимает кнопку прикрепления видео.
4. Flutter через `image_picker` выбирает видеофайл.
5. Файл кодируется в base64.
6. Flutter вызывает `client.training.uploadSetVideo`.
7. Сервер получает файл, сохраняет его в `web/static/uploads/videos`.
8. В базе создается запись `WorkoutVideo`.
9. Когда тренер или спортсмен открывает видео, приложение строит ссылку на файл и открывает его.
10. Комментарии тренера хранятся отдельно в `video_comment`.
11. При показе комментариев приложение берет `coachId` из комментария, получает пользователя-тренера и показывает его фото рядом с текстом.

Это сделано максимально просто для демо-проекта. Для полноценного продакшена обычно добавляют отдельное файловое хранилище, например S3, Firebase Storage или другой storage.

## 9. Как работают фотографии профиля и взаимное отображение

Раньше фото профиля было в основном локальным: пользователь мог видеть его у себя, но другой пользователь не мог надежно получить это фото. Теперь фото профиля стало частью серверных данных пользователя.

Порядок такой:

1. Пользователь выбирает фото в профиле.
2. Flutter получает файл через `image_picker`.
3. Файл кодируется в base64.
4. Flutter вызывает `client.user.uploadProfileImage`.
5. Серверный метод `UserEndpoint.uploadProfileImage` сохраняет файл в `coach_app_server/web/static/uploads/avatars`.
6. В таблице `app_user` обновляется поле `imagePath`.
7. Когда пользователь двигает фото или меняет масштаб и нажимает “Сохранить профиль”, Flutter вызывает `client.user.updateProfileImageFrame`.
8. Сервер сохраняет `imageScale`, `imageOffsetX` и `imageOffsetY`.
9. Если пользователь удаляет фото, вызывается `client.user.removeProfileImage`, старый файл удаляется, а `imagePath` и параметры кадра очищаются.

За отображение отвечает общий виджет `AvatarPreview`. Он умеет показывать:

- локальный файл, если фото только что выбрали;
- серверный путь вида `uploads/avatars/...`;
- сохраненный кадр: масштаб и сдвиг фото внутри круга;
- запасной круг с инициалами или иконкой, если фото нет.

Как это работает между тренером и спортсменом:

- тренер получает список спортсменов через `client.coach.listAthletes`, и каждый объект `User` уже содержит `imagePath`, `imageScale`, `imageOffsetX`, `imageOffsetY`, поэтому в карточке спортсмена можно показать фото ровно в том кадре, который спортсмен выбрал у себя в профиле;
- при выборе спортсмена фото также показывается в шапке выбранного спортсмена;
- спортсмен на главной получает своего закрепленного тренера через `client.coach.getCoachForAthlete(userId)`;
- это не список тренеров, а один текущий закрепленный тренер, поэтому интерфейс остается простым;
- карточка тренера у спортсмена показывает фото, имя и контакт тренера, тоже с учетом кадрирования из профиля тренера.

То есть фото не копируются отдельно между пользователями. У каждого пользователя есть `imagePath` и параметры кадра, а другие экраны просто читают эти поля и показывают актуальную фотографию так же, как она настроена в профиле.

## 10. Как работает офлайн-режим

Офлайн-режим сделан не как полноценная синхронизация, а как локальный кэш.

Это значит:

- если сервер доступен, приложение берет свежие данные с сервера;
- после загрузки сохраняет копию в `SharedPreferences`;
- если сервер недоступен, приложение показывает последнюю сохраненную копию.

За это отвечает `OfflineCache`.

Пример:

1. Спортсмен открыл календарь.
2. Приложение загрузило тренировки с сервера.
3. Эти тренировки сохранились локально.
4. Потом сервер отключили.
5. Приложение не зависает навсегда, а показывает сохраненные тренировки.

Важно для защиты: это не полноценная офлайн-first система, где можно долго работать без интернета и потом автоматически синхронизировать изменения. Это демо-реализация кэша, чтобы пользователь не видел пустой экран при проблемах с сервером.

## 11. Как строится прогресс

График рабочего веса строится не из случайных чисел, а из реально введенных подходов.

Логика такая:

1. Сервер берет тренировки пользователя.
2. В каждой тренировке берет упражнения.
3. В каждом упражнении берет подходы.
4. Для каждого упражнения выбирает максимальный вес из подходов.
5. Создает точки графика: дата тренировки, упражнение, максимальный вес.
6. Flutter рисует эти точки на графике.

Если спортсмен не вводил подходы, график не должен показывать выдуманный прогресс.

График собственного веса строится из таблицы `body_weight_entry`. Когда пользователь меняет вес в профиле, сервер сохраняет запись с датой.

### `coach_app_server/bin/admin.dart`

Служебная консоль администратора. Это не экран приложения, а команда для человека, который сопровождает систему на сервере.

Что умеет:

- `users` - показать всех пользователей и их роли;
- `links` - показать все привязки тренер-атлет;
- `exercises` - показать упражнения из библиотеки;
- `set-role` - назначить пользователю роль тренера или атлета;
- `attach` - привязать атлета к тренеру;

- `delete-exercise` - удалить упражнение из библиотеки.

Этот файл работает через PostgreSQL в Docker. Поэтому перед запуском административных команд должна быть поднята база:

```bash
docker compose up -d
```

На защите можно объяснить так: администратор не смешан с обычным мобильным интерфейсом, потому что это служебная роль. Он контролирует роли, привязки и справочник упражнений через серверную консоль, а приложение использует уже готовые данные из таблиц `app_user`, `coach_athlete` и `exercise`.

### `coach_app_server/lib/server.dart`

Главный файл настройки Serverpod.

Он:

- создает объект `Serverpod`;
- подключает сгенерированные endpoints;
- подключает протокол моделей;
- настраивает web-сервер;
- раздает статические файлы из `web/static`;
- раздает Flutter web-приложение из `/app`, если оно собрано;
- добавляет маршрут для `assets/config.json`;
- запускает сервер.

Для защиты можно сказать: это центральная точка конфигурации backend-части.

### `coach_app_server/lib/src/users/user_endpoint.dart`

Endpoint для пользователей.

Основные методы:

- `getUser` - получить пользователя по id;
- `register` - зарегистрировать пользователя;
- `login` - войти по контакту и паролю;
- `updateProfile` - обновить рост, вес и возраст;
- `updateAccount` - обновить имя и контакт;
- `uploadProfileImage` - загрузить фото профиля на сервер;
- `removeProfileImage` - удалить фото профиля;
- `updateProfileImageFrame` - сохранить масштаб и сдвиг фото внутри круглого аватара;
- `listBodyWeights` - вернуть историю веса тела;
- `_hashPassword` - превратить пароль в хэш SHA-256 с демо-солью;
- `_passwordMatches` - сравнить введенный пароль с сохраненным хэшем;
- `_isPasswordHash` - понять, пароль уже сохранен как хэш или это старая демо-запись;
- `_saveBodyWeightIfNeeded` - если пользователь ввел новый вес, сохранить его в историю;
- `_buildStoredAvatarName`, `_safeExtension`, `_deleteStoredAvatar` - служебные методы для безопасного имени файла, проверки расширения и удаления старого аватара.

Именно здесь находится логика аккаунта. При регистрации сервер проверяет, что имя, контакт и пароль не пустые, приводит контакт к единому виду и больше не записывает пароль в базу напрямую: сначала он очищает лишние пробелы, добавляет простую демо-соль `coach_app_demo_salt_v1`, считает SHA-256 и сохраняет строку вида `sha256:v1:...`. При входе сервер хэширует введенный пароль таким же способом и сравнивает результат с тем, что лежит в базе. Если аккаунт был создан раньше и там еще лежит старый обычный пароль, сервер один раз разрешает вход и сразу перезаписывает пароль уже в виде хэша.

После последних изменений этот endpoint отвечает не только за текстовые данные профиля и базовую защиту пароля, но и за серверное хранение аватаров. Фото сохраняется в `web/static/uploads/avatars`, в `app_user.imagePath` записывается путь к файлу, а в `imageScale`, `imageOffsetX`, `imageOffsetY` сохраняется выбранный пользователем кадр.

### `coach_app_server/lib/src/coaches/coach_endpoint.dart`

Endpoint для роли тренера.

Основные методы:

- `attachAthleteByContact` - закрепить спортсмена за тренером по контакту;
- `listAthletes` - получить всех спортсменов тренера;
- `getCoachForAthlete` - получить одного закрепленного тренера для спортсмена;
- `listAthleteWorkouts` - получить тренировки выбранного спортсмена;
- `createWorkoutForAthlete` - назначить спортсмену тренировку;
- `updateAthleteWorkout` - изменить тренировку спортсмена;
- `deleteAthleteWorkout` - удалить тренировку спортсмена;
- `_hasAthleteAccess` - проверка прав доступа.

Главная мысль: тренер не может смотреть всех спортсменов подряд. Он работает только с теми, кто закреплен за ним через `coach_athlete`. Для спортсмена не сделан отдельный список всех тренеров: используется простой метод `getCoachForAthlete`, который возвращает одного закрепленного тренера, чтобы показать его фото и имя на главной.

### `coach_app_server/lib/src/training/training_endpoint.dart`

Самый большой endpoint, отвечающий за тренировки.

Основные методы:

- `listExercises` - получить библиотеку упражнений;
- `listWorkouts` - получить тренировки пользователя;
- `getWorkoutsForMonth` - тренировки за месяц;
- `getUpcomingWorkout` - ближайшая тренировка;
- `createWorkout` - создать тренировку спортсменом;
- `updateWorkout` - редактировать тренировку;
- `deleteWorkout` - удалить тренировку;
- `addExerciseToWorkout` - добавить упражнение в тренировку;
- `listWorkoutExercises` - получить упражнения тренировки;
- `addSet` - добавить подход;
- `listSets` - получить подходы упражнения;
- `uploadSetVideo` - загрузить видео к подходу;
- `listSetVideos` - получить видео конкретного подхода;
- `listWorkoutVideos` - получить все видео тренировки;
- `addVideoComment` - добавить комментарий тренера;
- `listVideoComments` - получить комментарии к видео;
- `getProgress` - посчитать точки прогресса рабочего веса;
- `_ensureExerciseLibrary` - заполнить библиотеку упражнений базовыми упражнениями.

### `coach_app_server/lib/src/training/workout_delete_helper.dart`

Помощник для удаления тренировки.

Он удаляет не только строку тренировки, а все связанные данные:

- `migration_registry.txt` - список миграций.

## 19. Flutter-приложение: общая логика

Flutter-приложение находится в:

```text
coach_app_flutter/lib
```

Главная идея:

- экран входа/регистрации получает пользователя;

## 20. Flutter-файлы по одному

### `lib/main.dart`

Главный файл приложения.

Что делает:

- запускает Flutter;
- определяет адрес Serverpod-сервера через `resolveServerUrl`;
- создает глобальный `Client`;
- проверяет, есть ли сохраненная сессия;
- открывает либо `LoginScreen`, либо `RoleGate`;
- `RoleGate` решает, спортсмен это или тренер;
- `MainNavigationScreen` создает нижнюю навигацию спортсмена.

### `lib/app_config.dart`

Отвечает за адрес сервера.

Проблема, которую он решает: на Android-эмуляторе `localhost` внутри эмулятора - это сам эмулятор, а не компьютер. Поэтому файл пробует варианты:

- `10.0.2.2:8080`;
- `127.0.0.1:8080`;
- адрес из `--dart-define=SERVER_URL`.

Это нужно, чтобы приложение могло подключиться к серверу и на Windows, и в браузере, и на Android-эмуляторе.

Также здесь есть `resolveWebServerUrl`. Он нужен для статических файлов: видео подходов и фотографий профиля. API работает через порт `8080`, а файлы Serverpod раздает через web-сервер, обычно на порту `8082`.

### `lib/server_probe_io.dart`

Проверяет TCP-подключение к серверу на обычных платформах, например Android или Windows.

Если адрес отвечает, приложение выбирает его.

### `lib/server_probe_stub.dart`

Заглушка для платформ, где TCP-проверка недоступна, например web.

### `lib/server_request.dart`

Обертка для запросов к серверу.

Главная функция `waitForServer` ставит таймаут 10 секунд. Это нужно, чтобы приложение не висело бесконечно, если сервер не отвечает.

### `lib/user_cache.dart`

Сохраняет данные пользователя локально:

- id;
- имя;
- контакт;
- роль;
- рост;
- вес;
- возраст;
- серверный путь к фото профиля, если он есть.

Используется после входа, регистрации и обновления профиля. Если сервер вернул пустой `imagePath`, локальный путь к фото очищается, чтобы приложение не показывало старый аватар.

### `lib/offline_cache.dart`

Локальный кэш данных.

Сохраняет в `SharedPreferences`:

- упражнения;
- тренировки за месяц;
- ближайшую тренировку;
- упражнения внутри тренировки;
- подходы;
- прогресс;
- историю веса тела.

Это позволяет показывать последние сохраненные данные, если сервер временно недоступен.

### `lib/login_screen.dart`

Экран входа.

Основное:

- пользователь выбирает роль: спортсмен или тренер;
- вводит телефон/email и пароль;
- вызывается `client.user.login`;
- сервер хэширует введенный пароль и сравнивает его с хэшем в базе;
- если роль аккаунта не совпадает с выбранной вкладкой, показывается ошибка;
- после успешного входа данные сохраняются и открывается `RoleGate`.

### `lib/registration_screen.dart`

Экран регистрации.

Основное:

- пользователь выбирает роль;
- вводит имя, контакт, пароль и подтверждение;
- приложение проверяет, что поля заполнены и пароли совпадают;
- пользователь должен поставить галочку согласия на обработку персональных данных;
- без этой галочки кнопка регистрации остается неактивной, поэтому случайно создать аккаунт без согласия нельзя;
- ссылка `Подробнее` открывает нижний информационный блок: там простым языком написано, какие данные используются и зачем;
- вызывает `client.user.register`;
- сервер сохраняет не открытый пароль, а его SHA-256 хэш;
- если логин занят, сервер возвращает `null`;
- после успешной регистрации открывается нужный интерфейс.

Этот блок нужен потому, что при регистрации пользователь вводит телефон или email, а это относится к персональным данным. В демо-версии согласие реализовано на уровне интерфейса: приложение не дает нажать кнопку регистрации, пока пользователь не подтвердит, что ознакомился с условиями обработки данных.

## 24. Как объяснить запуск системы

Для работы нужны:

1. Docker с PostgreSQL.
2. Serverpod-сервер.
3. Flutter-приложение.

Типовой запуск:

```bash
cd coach_app_server
docker compose up -d
dart bin/main.dart --apply-migrations
```

Потом Flutter:

```bash
cd coach_app_flutter
flutter run
```

Для Android-эмулятора может понадобиться проброс портов:

```bash
adb reverse tcp:8080 tcp:8080
adb reverse tcp:8082 tcp:8082
```

Сервер API обычно работает на `8080`, inspector/logging на `8081`, web-сервер на `8082`.

## 25. Что можно сказать на защите коротко

Можно сказать так:

“Моя информационная система состоит из Flutter-клиента, Serverpod-сервера и PostgreSQL базы данных. Пользователь регистрируется как спортсмен или тренер. Роли хранятся в базе в поле `isAthlete`, а администратор может управлять ими через серверную консоль без отдельного мобильного интерфейса. Пароль не хранится в базе открытым текстом: сервер сохраняет его SHA-256 хэш с демо-солью. Спортсмен ведет тренировки, добавляет упражнения, подходы, рабочие веса и видео. Тренер закрепляет спортсменов по контакту, назначает им тренировки, смотрит историю, открывает видео подходов и оставляет комментарии. При этом тренер тоже может вести свои личные тренировки и график прогресса в том же аккаунте, но спортсмен автоматически тренером не становится. У спортсмена отображается карточка закрепленного тренера с фото, а у тренера отображаются карточки спортсменов с их фото. Сервер хранит данные в связанных таблицах: пользователи, тренировки, упражнения, подходы, видео и комментарии. Файлы видео и фото профиля лежат на сервере, а в базе хранится путь к ним. Графики строятся не на случайных данных, а на основе реально введенных подходов и веса пользователя. Для удобства реализован локальный кэш, чтобы при недоступном сервере приложение показывало последние сохраненные данные.”

## 26. Что важно честно сказать

Система сейчас находится в демонстрационном локальном состоянии.

Это значит:

- пароль уже не хранится открытым текстом: для демо используется SHA-256 с фиксированной солью, но для реального продукта лучше использовать bcrypt, Argon2 или PBKDF2 с отдельной солью для каждого пользователя;
- модель `User` в демо все еще содержит поле `password`, поэтому для промышленной версии хэш пароля лучше вообще не отдавать клиентскому приложению;
- видео и фото профиля хранятся локально на сервере, для продакшена лучше использовать отдельное файловое хранилище;
- офлайн-режим показывает сохраненные данные, но пока не делает полноценную двустороннюю синхронизацию;
- авторизация сделана упрощенно через свой `UserEndpoint`; стандартный Serverpod Auth убран из проекта, чтобы не держать второй неиспользуемый механизм входа;
- согласие на обработку персональных данных сейчас проверяется на экране регистрации. Для промышленной версии лучше дополнительно сохранять в базе дату согласия, версию текста согласия и источник подтверждения.

Это нормально для дипломного прототипа, но на защите лучше показать, что ты понимаешь, чем демо отличается от промышленной версии.
